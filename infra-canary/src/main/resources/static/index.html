Actuator health off

Sets component chaos of /actuator/health. Monitoring sees DOWN (HTTP 503); Kubernetes probes are not affected.

Readiness: refuse traffic off

Readiness probe answers 503: the pod turns NotReady and leaves the Service endpoints. Use the control address (publishes not-ready pods) to keep this page reachable.

Liveness: broken off

Liveness probe answers 503. After 3 failed probes (~30 s) the kubelet restarts the container, which clears every fault. Watch RESTARTS in kubectl get pod.

Memory pressure off

Really allocates and touches memory. heap raises jvm_memory_used_bytes (capped at 90% of max heap unless OOM is allowed). direct is off-heap: enough of it gets the container OOMKilled at limits.memory.

CPU burn off

Busy-loop threads. With a CPU limit you see throttling (container_cpu_cfs_throttled); without one, the node's CPU rises. Probes may slow down.

Latency off

Delays every app request (/canary, /hello, …). Tick actuator too to slow the probes as well: past the 1 s probe timeout they count as failures.

HTTP errors off

A share of app requests fail with the chosen status (actuator and this console are never failed). Shows up in http_server_requests_seconds_count{status="5xx"}.

Fill the log volume off

Writes .chaos-fill next to the log file: the Longhorn volume (replica on nas-server). Fill it completely to see the app's log writes and /canary log-volume check fail.

Mock metric values

Only numbers: published as canary_mock_value{name="…"} on /actuator/prometheus to drive Grafana panels and alert rules without stressing anything.

Logs & checks

Existing canary endpoints: everything lands in /app/logs/canary/infra-canary.log.

Crash the JVM

exit runs shutdown hooks (like SIGTERM); halt stops at once (like a segfault). Either way Kubernetes restarts the container (CrashLoopBackOff if repeated quickly).
